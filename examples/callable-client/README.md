# ayjnt example: callable-client

Demonstrates the **Cloudflare Agents `@callable()` decorator** — agent
methods callable directly from a browser UI over WebSocket via
`agent.stub.method(args)`, with the same decorator also driving
inclusion in `/__ayjnt/catalog`.

The example shows the **two "callable" patterns** that exist in this
framework after the unification:

1. **`@callable()` decorator from `"agents"`** — primary. Makes the
   method browser-callable AND lists it in the catalog. One source of
   truth for the public RPC surface.
2. **`/** @callable */` JSDoc tag** — legacy fallback. Useful only for
   catalog-only methods (no browser exposure). Most code shouldn't
   need it.

The third "callable" path — agent-to-agent RPC via `getAgent<T>` —
doesn't need either marker; TypeScript's `public` is enough.
See `examples/inter-agent` for that.

## What the agent looks like

```ts
import { Agent, callable } from "agents";
import type { GeneratedEnv } from "@ayjnt/env";

export default class NotesAgent extends Agent<GeneratedEnv, State> {
  override initialState: State = { notes: [] };

  /** Add a note. The agent generates the id; only the server can. */
  @callable({ description: "Add a new note." })            // ← drives both browser RPC AND catalog
  async addNote(text: string): Promise<Note> {
    const note = { id: crypto.randomUUID(), text, createdAt: Date.now() };
    this.setState({ notes: [...this.state.notes, note] });
    return note;                                            // ← typed return
  }
}
```

The decorator's `description` option becomes the catalog description.
The long-form JSDoc above the method stays for editor hover — it's
developer docs, not catalog content. If the decorator has no
`description` option, the catalog falls back to the JSDoc's first
prose line.

## What the UI looks like

```tsx
import { useAgent } from "@ayjnt/notes";
import type { NotesAgent } from "@ayjnt/notes";

export default function NotesApp() {
  const agent = useAgent<NotesAgent>();
  const submit = async () => {
    const note = await agent.stub.addNote("hello");  // typed end-to-end
    console.log("created", note);                     // { id, text, createdAt }
  };
  // ...
}
```

`agent.stub` is a proxy generated by the Agents SDK from the
`NotesAgent` type — every `@callable()`-decorated method appears
with full TypeScript autocomplete.

## Why this matters

Before this example, the closest pattern was `agent.setState({...})`
from `examples/with-ui` — a state-replacement op the SDK round-trips
for you. That works when the change *is* the new state. It doesn't
work for:

- **Server-generated values.** "Create with a fresh UUID" can't be
  expressed by replacing state — only the server knows the new id.
- **Conditional logic the client can't run.** "Delete if exists",
  "decrement only if positive", "verify a secret before applying".
- **Derived values.** "How many notes match this filter?" — let the
  server count and return; don't re-implement on the client.
- **Anything that should fail at the boundary.** Throw from the
  callable; the Promise rejects on the client. Trying to express
  validation via state replacement loses the error path.

`@callable()` methods give you all of that with a single decorator
and a typed proxy on the client.

## How the patterns layer

| Pattern | Marker | Caller | Transport |
|---|---|---|---|
| **CF `@callable()`** | `@callable({ description })` from `"agents"` | Browser UI via `agent.stub.method()` AND catalog consumers | WebSocket frame + build-time catalog |
| **ayjnt `/** @callable */`** | JSDoc tag (catalog-only fallback) | `/__ayjnt/catalog` JSON consumers — but NOT the browser | Build-time catalog only |
| **ayjnt `getAgent<T>`** | None — TypeScript `public` is enough | Other agents inside the worker | Native DO RPC |

The decorator covers both browser-callability and catalog inclusion
with one marker. The JSDoc tag is a fallback for the rare
catalog-only case (e.g., an agent-to-agent RPC method you want
discoverable). `getAgent<T>` works against any public method
regardless of decoration — `_findById` in `agent.ts` shows this.

## Run it

```sh
bun install
bun run dev
# open http://localhost:8787/notes
# open the same URL in a second tab — every add/delete syncs live
```

`/notes` defaults to instance `"default"`. `/notes/team-a` and
`/notes/team-b` are independent — different teams, different note
lists.

## External client — `client.ts`

The React UI in `app.tsx` calls `@callable` methods via
`agent.stub.method(...)` because the framework's generated
`useAgent()` hook wraps that for you. **The same surface is available
to any standalone script** (Bun, Node, Deno) via the Cloudflare Agents
SDK's `AgentClient` class. `client.ts` in this folder is a working
example:

```ts
import { AgentClient } from "agents/client";
import type NotesAgent from "./agents/notes/agent.ts";

const client = new AgentClient<NotesAgent>({
  agent: "NotesAgent",                       // ignored when basePath is set
  basePath: `notes/${instance}`,             // bypasses default URL construction
  host: "localhost:8787",
  onStateUpdate: (state, source) =>
    console.log(`${state.notes.length} notes (${source})`),
  onIdentity: (name, agent) =>
    console.log(`connected to ${agent}#${name}`),
});

await client.ready;                          // wait for identity handshake

const note = await client.stub.addNote("hi");          // typed!
const total = await client.stub.countNotes();          // typed!
await client.call("deleteNote", [note.id]);            // untyped fallback

client.close();
```

The `<NotesAgent>` generic binds `client.stub` to the agent class — every
`@callable()`-decorated method is on the stub with full type checking.

### Run it

```sh
# Terminal 1: dev server up
bun run dev

# Terminal 2: external client
bun run client
# or against a deployed worker:
HOST=https://my-app.workers.dev INSTANCE=team-a bun run client
```

Expected output (rough):

```
[identity] connected to NotesAgent#default
[state push from server] 0 note(s): []
[state push from server] 1 note(s): [ 'from the external client' ]
addNote -> { id: '…', text: 'from the external client', createdAt: … }
[state push from server] 2 note(s): [ 'from the external client', 'second note' ]
addNote -> { id: '…', text: 'second note', createdAt: … }
countNotes -> 2
[state push from server] 1 note(s): [ 'second note' ]
deleteNote -> true
[state push from server] 0 note(s): []
after clear -> 0
```

State pushes arrive over the same WebSocket — `onStateUpdate` fires
once on connect (with the current state) and again after every
`setState({...})` on the agent, regardless of whether *this* client
triggered the change.

### When to use `AgentClient` vs `agentFetch`

| Need | Use |
|---|---|
| Call `@callable()` methods (RPC) | `AgentClient` (WebSocket) |
| Live state pushes via `onStateUpdate` | `AgentClient` (WebSocket) |
| One-shot HTTP request → response | `agentFetch` |
| Don't want to manage a long-lived connection | `agentFetch` |

`AgentClient` is the right pick for any script that's going to make
more than one call or wants to observe state. `agentFetch` is for the
"single round-trip" case — see [`examples/with-client`](../with-client)
for that pattern.

## Curl-level inspection

```sh
# Read the JSON state (HTTP — hits onRequest)
curl http://localhost:8787/notes/default

# See the catalog metadata (the @callable JSDoc surface)
curl http://localhost:8787/__ayjnt/catalog | jq '.agents[] | select(.routePath == "/notes")'
```

Curl can't drive the WebSocket RPC channel — use `client.ts` or the
React UI for that.
